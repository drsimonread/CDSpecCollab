## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification (SRS) defines the current scope and externally observable requirements of the Circular Dichroism Spectrometer (CD Spec) web application. It is the baseline for implementation, quality assurance, documentation, and future planning. Requirements marked **Implemented** describe behavior present in the current repository. Requirements marked **Planned** identify work that is in scope for a future iteration but is not represented as completed functionality.

### 1.2 Scope

CD Spec is a browser-based Django application for storing, controlling access to, and visualizing circular dichroism spectroscopy runs. The application accepts instrument CSV files, parses their headers and measurement rows, stores the resulting run in PostgreSQL through the Django ORM, and presents individual or multiple runs as graphs.

The current release includes:

* A Django 4.2 web application served through WSGI.
* PostgreSQL persistence using Django models and migrations.
* Local account authentication and Google OAuth through `django-allauth`.
* Permission-controlled upload, edit, delete, and visibility operations.
* CSV ingestion for the supported CD spectrometer format.
* Single-run and multi-run data visualization using Plotly.
* Django admin and user-management routes.

The current release does not include a native desktop application, a separate mobile application, a general-purpose scientific analysis package, or a completed dataset download endpoint. Email delivery, Google credentials, database credentials, and production host configuration remain deployment concerns and must not be hard-coded in a production environment.

### 1.5 System Overview

The application provides a shared web interface for research and education users. A visitor can view runs explicitly marked public. An authenticated user can access runs according to the permissions assigned to that account. Authorized users can upload supported CSV files, review parsed metadata, and manage visibility. The system stores raw measurement data as JSON together with run metadata and source-file information.

The application is organized as a Django project:

1. Django URL configuration routes requests to the CD Spec, user, authentication, and administrative applications.
2. Django templates and Bootstrap-based form rendering provide the browser interface.
3. Django views enforce permission checks and coordinate form processing.
4. The `SpecRun` model and migrations define persistence in PostgreSQL.
5. `django-allauth` provides account and Google OAuth integration.
6. Plotly renders stored measurements in the browser.

## 2. Functional Requirements

### 2.1 Authentication and Accounts

* **FR-AUTH-01 — Implemented:** The system shall provide account registration, sign-in, sign-out, password change, password reset, and email verification through the account routes.
* **FR-AUTH-02 — Implemented:** The system shall support sign-in with Google OAuth when the deployment has a configured Google social application.
* **FR-AUTH-03 — Implemented:** The system shall use the project’s custom Django user model and email-based authentication configuration.
* **FR-AUTH-04 — Implemented:** The system shall protect authenticated user profile and update views from unauthenticated access.
* **FR-AUTH-05 — Implemented:** The system shall use Django’s password hashing, session, CSRF, and authentication middleware.
* **FR-AUTH-06 — Planned:** Production deployment shall load secret keys, OAuth credentials, email credentials, and database credentials from a protected configuration source rather than source code.

### 2.2 Access Control and Visibility

* **FR-ACCESS-01 — Implemented:** The system shall support public, student-level, and administrator-level access through Django permissions and run visibility flags.
* **FR-ACCESS-02 — Implemented:** A visitor shall be able to view only runs marked `visible_public`.
* **FR-ACCESS-03 — Implemented:** A user with the student-view permission shall be able to view runs marked public or student-visible.
* **FR-ACCESS-04 — Implemented:** A user with the view-all permission shall be able to view runs regardless of their visibility flags.
* **FR-ACCESS-05 — Implemented:** Upload, edit, and delete operations shall require their corresponding Django model permission.
* **FR-ACCESS-06 — Implemented:** A run editor shall be able to change its title, description, and student/public visibility settings.
* **FR-ACCESS-07 — Planned:** Administrator and student permissions shall be documented and provisioned through a repeatable deployment or administration procedure.

### 2.3 Run Catalog and Navigation

* **FR-CATALOG-01 — Implemented:** The system shall provide a CD Spec index at `/cdspec/`.
* **FR-CATALOG-02 — Implemented:** The index shall display recent runs, including title, operator, uploader, run date, and number of data points.
* **FR-CATALOG-03 — Implemented:** The system shall provide a detail page for an individual run.
* **FR-CATALOG-04 — Implemented:** The system shall provide a view of runs uploaded by a specified user.
* **FR-CATALOG-05 — Implemented:** The system shall provide an About page and authenticated user profile routes.
* **FR-CATALOG-06 — Planned:** The index shall provide a server-backed search and filtering feature. The current search control is presentation-only and is not treated as a completed requirement.

### 2.4 Data Ingestion and Storage

* **FR-DATA-01 — Implemented:** An authorized user shall be able to submit a CSV source file with run metadata and calculation inputs.
* **FR-DATA-02 — Implemented:** The ingestion process shall read the supported instrument header fields through the `XYDATA` marker and parse the declared number of numeric data rows.
* **FR-DATA-03 — Implemented:** The system shall store the original CSV as a source file associated with the run.
* **FR-DATA-04 — Implemented:** The system shall store run title, description, operator, run date, upload date, uploader, visibility flags, calculation inputs, data-point count, axis units, and parsed raw data.
* **FR-DATA-05 — Implemented:** The system shall reject unsupported file extensions at the model form boundary and report an error when the CSV cannot be parsed.
* **FR-DATA-06 — Implemented:** An authorized user shall be able to edit supported run metadata after upload.
* **FR-DATA-07 — Implemented:** An authorized user shall be able to delete a stored run through the delete route.
* **FR-DATA-08 — Planned:** The ingestion process shall provide field-level validation and user-facing error details for missing headers, malformed numeric rows, inconsistent point counts, and oversized files.
* **FR-DATA-09 — Planned:** The system shall provide a controlled download or export operation for authorized users. No download endpoint is part of the current implementation.

### 2.5 Visualization

* **FR-VIZ-01 — Implemented:** The detail page shall render a run’s X and Y data as a Plotly line graph.
* **FR-VIZ-02 — Implemented:** The graph shall use the stored axis-unit labels when available.
* **FR-VIZ-03 — Implemented:** The system shall support optional additional Y-series data when the source file provides it.
* **FR-VIZ-04 — Implemented:** The system shall provide a multi-graph route for selecting multiple runs.
* **FR-VIZ-05 — Implemented:** The multi-graph operation shall prevent comparison of runs with incompatible axis-unit metadata.
* **FR-VIZ-06 — Planned:** The visualization interface shall expose user controls for selecting graph parameters and displaying supported additional axes, including temperature or voltage where present in the source data.

### 2.6 Administration and Operations

* **FR-ADMIN-01 — Implemented:** The system shall expose Django admin for authorized administrators.
* **FR-ADMIN-02 — Implemented:** Database schema changes shall be represented by Django migrations.
* **FR-ADMIN-03 — Implemented:** The application shall write operational messages through Django’s logging configuration.
* **FR-ADMIN-04 — Planned:** Production operations shall define backup, restore, migration, monitoring, and credential-rotation procedures.

## 3. Non-Functional Requirements

### 3.1 Security

* **NFR-SEC-01:** Production deployments shall run with `DEBUG` disabled and with a restricted `ALLOWED_HOSTS` list.
* **NFR-SEC-02:** Production deployments shall use HTTPS and secure cookie settings.
* **NFR-SEC-03:** The application shall use Django CSRF protection and permission checks for state-changing operations.
* **NFR-SEC-04:** Secrets shall not be committed to the repository.
* **NFR-SEC-05:** User and data access failures shall be reported as an explicit authorization response or redirect; the application shall not silently grant access.

### 3.2 Compatibility and Usability

* **NFR-USE-01:** The application shall be usable through a current version of a supported desktop or mobile web browser.
* **NFR-USE-02:** The application shall provide HTML responses that remain usable at the configured Bootstrap responsive breakpoints.
* **NFR-USE-03:** Forms shall display validation feedback when submitted data is invalid.
* **NFR-USE-04:** The application shall use the configured project time zone, currently `America/New_York`, for displayed and stored timestamps.

### 3.3 Maintainability

* **NFR-MAINT-01:** The application shall target Python and Django versions declared by the project dependency requirements.
* **NFR-MAINT-02:** Application behavior shall be covered by automated tests for authentication, user routes, permissions, parsing, and run workflows as those areas are implemented.
* **NFR-MAINT-03:** Requirements, design, test, and deployment documents shall describe the same current scope and technology stack.

### 3.4 Performance and Reliability

* **NFR-PERF-01:** The application shall use PostgreSQL as the production relational database.
* **NFR-PERF-02:** The application shall return a clear error response when the database, authentication provider, or source-file parser cannot complete a request.
* **NFR-PERF-03 — Planned:** Deployment shall define dataset-size limits and request time targets for upload, index, detail, and visualization operations.

## 4. External Interfaces

### 4.1 User Interface

The browser interface shall provide:

* Account and authentication pages under `/accounts/`.
* User profile and update pages under `/users/`.
* CD Spec catalog, upload, detail, edit, delete, and multi-graph pages under `/cdspec/`.
* An About page at `/about/`.
* Django admin at `/admin/`.

### 4.2 File Interface

The current upload interface accepts CSV files. A supported file contains instrument metadata rows, an `XYDATA` marker, and numeric measurement rows. The `NPOINTS` header determines how many measurement rows are read. The source file is retained with the stored run.

### 4.3 Database Interface

The application uses Django’s ORM and migration system with PostgreSQL. The primary domain entity is `SpecRun`, which stores run metadata, visibility state, source-file reference, parsed JSON data, and axis information.

### 4.4 Authentication and Email Interfaces

Local account services are provided by Django and `django-allauth`. Google OAuth is available through the configured Google social-account provider. Email verification and password-reset delivery use the configured Django email backend. These external services must be configured separately for each deployment.

### 4.5 Client-Side Visualization Interface

Run graphs are rendered in the browser with Plotly. The deployment must make the Plotly client library available to the templates, either through the current client-side distribution or an approved equivalent.

## 5. System and Deployment Requirements

### 5.1 Server

The deployment shall provide:

* A supported Python runtime for the versions declared by the project.
* Django and the pinned Python dependencies in `cd_spec_viewer_web/requirements.txt`.
* PostgreSQL and a database user with the required migration permissions.
* A WSGI-compatible application server or hosting platform.
* Persistent storage for uploaded source files.
* HTTPS and a DNS name for production use.

### 5.2 Client

The client shall provide:

* A current browser with JavaScript enabled.
* Network access to the deployed application.
* A display and input method suitable for browser use.

The application is not a standalone desktop program and does not require a locally installed database or instrument driver for ordinary browser access.

### 5.3 Configuration

Before production release, operators shall configure the secret key, allowed hosts, database connection, site ID, Google OAuth application, email backend, static-file serving, media-file serving, and HTTPS settings without exposing credentials in source control.

## 6. Delivery and Acceptance

An iteration satisfies this SRS baseline when:

1. Implemented functional requirements remain available through the documented routes.
2. Access checks prevent users from viewing or modifying runs outside their permissions.
3. A supported CSV can be uploaded, parsed, stored, and displayed as a graph.
4. An incompatible multi-graph selection is rejected with a user-facing message.
5. Automated tests pass for the changed behavior.
6. Deployment documentation identifies all required services and configuration values.
7. Any unimplemented or changed requirement is labeled Planned or updated in this document before release.

---

## 7. Out of Scope for the Current Baseline

The following are not requirements of the current implementation:

* A native Windows, macOS, or Linux desktop application.
* A separate iOS or Android application.
* Direct control of a circular dichroism instrument.
* Automatic scientific interpretation or molecular-structure modeling.
* A completed general search engine or data-export workflow.
* Bulk email campaigns or email notifications beyond account-service messages.
* A fixed hardware minimum such as a particular CPU, RAM, or screen resolution. Hosting capacity shall be selected according to the deployed dataset and traffic.
